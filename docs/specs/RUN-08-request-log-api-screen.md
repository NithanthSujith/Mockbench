# RUN-08 — Request-log API and screen

Status: done
Phase: 4   Team: Runtime
Depends on: RUN-07, BLD-04
Size: M

## Goal
At `/p/$projectSlug/logs` a user sees recent requests to the project — filterable, live-refreshing — and can tell a mocked error from a mock-server error at a glance.

## In scope
- Handler `requests.list` with filters and cursor pagination.
- The screen (TanStack Table): time, method badge, path, case, status chip, ms, from; filter bar (status class, method, path text, "mock-server errors only"); row expand for headers/query; auto-refresh toggle (3 s poll); empty states.

## Out of scope
The writer and pruner (RUN-07); export; charts.

## Contract
Endpoint `requests.list` (API-CONTRACT §3.10). Table `request_logs` (+ `versions.label` join). UI route `/p/$projectSlug/logs`.

## Acceptance criteria
- [x] `GET …/requests` returns newest first with `limit` (default 50, max 200), `nextCursor` over 120 rows pages 50/50/20; `limit=201` → `422`; a tampered cursor → `400 invalid_cursor`.
- [x] Filters AND together: `status=4xx` returns only 400–499; `status=404` only 404; `method=POST`; `path=invoices` matches case-insensitively as a substring; `since=<ts>` excludes older rows; `mockError=true` returns only rows with a non-null `mockError`.
- [x] Each item includes `versionLabel` (null when the version was deleted or the project was unpublished) and the redacted headers as stored; `ip` is present.
- [x] Viewer can read; a non-member gets `404`; the response parses against the registry schema.
- [x] The screen renders the prototype table; the status chip uses the 2xx/4xx/5xx classes; rows with `mockError` show a "mock server" tag and the hint text "mocked 404s are your own cases; these were generated by the server".
- [x] Changing a filter re-queries with the corresponding parameters and resets the cursor; "Load more" appends the next page.
- [x] Auto-refresh polls every 3 s only while the tab is visible, prepends new rows without losing scroll position, and can be paused.
- [x] Expanding a row shows request headers (redacted values shown as `[redacted]`) and query as mono key/value pairs.
- [x] A project with no requests shows "No requests yet. The log starts filling once this project is deployed."; one with no active version says the same plus a link to Versions.
- [x] The retention note says entries are pruned automatically, without hard-coded numbers unless the server exposes them (see Open questions).

## Implementation notes
- Backend: `apps/api/src/modules/requests/{index,service}.ts`; keyset cursor on `(created_at, id)` like `deployments.list`. `method` is matched case-insensitively (upper-cased), `path` is an escaped `ILIKE` substring, `since` is inclusive (`>=`), `mockError=false` returns only rows with a null `mockError`.
- Screen: `apps/web/src/features/logs/`. Filters (status class, method, path text with a 250 ms debounce, mock-server-only) live in the URL search (`validateSearch` in the logs route, schema in `features/logs/search.ts`; invalid values fall back to no filter) and form the Query key. Changes use `navigate({ search, replace: true })`; the path update to the URL keeps the 250 ms debounce. Added `zod` (already the stack validator) to `apps/web` for this.
- Auto-refresh re-fetches the loaded pages (`refetchInterval` 3 s, only while `document.visibilityState` is visible); rows are keyed by id so the DOM and scroll position are kept.
- Retention note is the generic "Older entries are pruned automatically." The open question (exposing `LOG_RETENTION_*` on `system.instance`) still needs a contract ruling.
- The Playwright poll test is covered by a Vitest fake-timer test instead (Playwright config is a shared file).
